# fs_overlay — Design Document

## Intro

`fs_overlay` is a prototype wrapper for running FHS-based programs on NixOS without using Bubblewrap. Bubblewrap restricts privilege escalation, preventing workflows such as using `sudo` in FHS shells, running `pkexec`, or writing files as root from editors like VS Code.

The goal of `fs_overlay` is to use mount namespaces only, preserving the ability to escalate privileges while safely overlaying parts of `/` (such as `/bin`, `/lib`, etc.) for a specific program.

You can use bind mounts or overlayfs. Overlayfs is only supported in kernels newer or equal to 6.13 because before then you could not use file descriptors to configure it using the new mount api.

The config files should be configured with the same care as sudo configuration files. `fs_overlay` should also be compiled with musl to have no dynamic dependencies.


## Trust Model

* Configs are trusted as root-equivalent and are expected to be generated by a NixOS module.
* The checks defend against tampering with configs, sources and targets, and against a hostile invoking user.
* The checks do not defend against a malicious config author.
* Trust in a source comes from the exact store path written in the root-owned config.


## High-Level Approach

* Use mount namespaces without user namespaces.
* Overlay or bind-mount directories and files as specified in a configuration file.
* Replace selected paths under `/` with controlled alternatives.
* After overrides set, execute the target program as the invoking user.



## Execution Model

Invocation format:

```
fs_overlay config_name program [args...]
```

`config_name` is a single file name looked up in `/etc/fs_overlay/`, not a path.

Execution steps:

1. Create a new mount namespace and recursively make `/` private.
2. Look for config file in `/etc/fs_overlay/` and validate configuration file integrity and permissions. This is done after step 1 because otherwise the fds would belong to the old mount namespace.
3. Validate the sources and targets of the overrides.
4. Apply directory and file overrides.
5. Drop privileges to the user and group who executed the `fs_overlay`
6. Execute the target program.



## Global Constraints
* All filesystem and mount operations must be performed through file descriptors obtained that have been verified to have correct permissions, ownership and etc.
* All mounts are readonly.
* All paths must be absolute and not contain any `..`.

## Mount Flags
Currently all mounts are only set `ro`

## Privilege and Permission Model

### fs_overlay Binary

* Must run as root.
* Intended to be setuid root.
* Behavior is driven entirely by configuration files.

### Configuration Files
* Must be owned by root:root.
* Must not be writable others.
* Parent directories must be owned by root:root.
* No special permission bits are allowed on the ancestors.
* Must be readable by others.



### Rules for sources of overides

Sources can only be under `/nix/store/` and `/run/wrappers`.

* `/nix/store` must be owned by root:anygroup, all other directories must be owned by root:root.
* Directories must not have the setuid or setgid bit set. The sticky bit is allowed.
* All files must be owned by root:root and not writable by others.
* All directories must be not writable by others and must be readable by everyone.
* Symlinks must point to a file/directory that follow the same rules as listed above.


## Config Format
Every override is a table with a `source` key.

* `source`: absolute path of the source, must follow the rules above.
* `overlayfs`: only used for directory overrides, ignored for file overrides. Defaults to `true`. When `true` the source is overlayed on top of the target, when `false` the source is bind mounted over the target.

### Example config
```toml
[overrides]
"/bin/bash" = { source = "/nix/store/x29azqwvawz9f6q57pin2srsn2ax8w08-example-bash/bash" }
"/usr" = { source = "/nix/store/x29azqwvawz9f6q57pin2srsn2ax8w08-example-fhs/usr", overlayfs = false }
```



## Known Limitations
* Targets must already exist. On NixOS `/lib`, `/usr/lib` and etc usually do not exist.
* Overlapping targets (e.g. `/usr` and `/usr/bin/foo`) are not supported. Overrides are stored in a `HashMap` so the mount order is not guaranteed.
